\section{Local Variable Names}\label{sec:NamesForLocalVariables}
\subsection{Names for Local Variables}
The identifiers for local variables have to be in \textit{camelCase}, with a lowercase first letter. Internal words start with capital letters, as already described in \tqvref{sec:CaseOfNames}. The names should contain neither the underscore (“\verb#_#”) nor any other special characters or non-ASCII letters, although allowed according to \jls \autocite{ORACLE_DOC_LANGUAGE_SPECIFICATION:Identifiers}; they also should not start with those characters. Digits are forbidden as first characters already by the language specification, otherwise they are allowed as additional characters. But they should be used with care and only were necessary.

Variable names should be short yet meaningful – with a clear priority on being meaningful. The choice of a variable name should be mnemonic – that is, designed to indicate the intent of its use to the casual observer. As for class names, abbreviations and acronyms should be avoided. Using the digit '\verb#4#' as replacement for the word “\verb#for#”, and '\verb#2#' for the word “\verb#to#” is acceptable, yet not really recommended.

Do not (never!) use a prefix to indicate the type of a variable (a practice known as \bsq{Hungarian Notation}\index{Hungarian Notation} \autocite{WIKIPEDIA:Hungarian_notation,Jack:HungarianNotation})! \Java is a strongly typed language and the compiler will take care that variables are only used according to their types.\footnote{While the use of the Hungarian Notation\index{Hungarian Notation} – in particular the \bsq{Systems Hungarian} variant – for the naming of variables is discouraged for strongly typed languages like Java, Scala\index{Scala} or \mbox{C++}\index{C++}, because it does not provide any benefit, this may be different for languages like PHP\index{PHP}, Python\index{Python}, C\index{C}, JavaScript\index{JavaScript} or even Groovy\index{Groovy}: for these languages the type prefix may help the programmers to assign the semantically correct type to a variable when syntactically any (or most) types are correct.}

Some quotes copied from Wikipedia \autocite{WIKIPEDIA:Hungarian_notation} with opinions about the \bsq{Hungarian Notation}\index{Hungarian Notation} – of course only those against it:
\begin{quote}
\bdq{Encoding the type of a function into the name (so-called Hungarian notation) is brain damaged – the compiler knows the types anyway and can check those, and it only confuses the programmer.} \\
Linus Torvalds
\end{quote}

\begin{quote}
\bdq{No I don't recommend \bsq{Hungarian}. I regard \bsq{Hungarian} (embedding an abbreviated version of a type in a variable name) as a technique that can be useful in untyped languages, but is completely unsuitable for a language that supports generic programming and object-oriented programming – both of which emphasize selection of operations based on the type and arguments (known to the language or to the run-time support). In this case, \bsq{building the type of an object into names} simply complicates and minimizes abstraction.} \\
Bjarne Stroustrup
\end{quote}

The use of the \lstinline|var|\index{var} keyword\footnote{Although \lstinline|var|\index{var} is a keyword (see \autocite{ORACLE_DOC_LANGUAGE_SPECIFICATION:Keywords}, it should be treated as a special type.} in Java programs does not weaken the strong typing of Java in any way – refer to chapter \tqfullvref{sec:LocalVariableTypeInference} – and is therefore no reason for using \bdq{Hungarian Notation}\index{Hungarian Notation}.

\keeplisting{7}
Usually you would use the singular form for a variable name, but for collections or arrays, the plural form can be perfectly correct:
\begin{lstlisting}
final Collection<Component> values = m_Components.values();
for( final Component value : values )
{
    …
}    
\end{lstlisting}

Using the name of the type for the variable (with a lower case first letter, of course) for the name of a local variable name is completely acceptable in case this is sufficient to explain the function of the variable; but prefixes like “\verb#my#” or “\verb#the#” must be avoided. And not all types are truly suitable as names for local variables; the best example of an unsuitable type is \lstinline|String|\index{java.lang!String}.
\keeplisting{9}
\begin{lstlisting}
// RECOMMENDED
public final String retrieveMessage( final String messageKey, final String... additionalInfo )
{
    final MessageProvider messageProvider = getMessageProvider();
    final var rawMessage = messageProvider.getMessage( messageKey );
    final var retValue = String.format( rawMessage, additionalInfo );
    
    //---* Done *----------------------------------------------------
    return retValue;
}   //  retrieveMessage()
\end{lstlisting}
\keeplisting{4}
Usually, you would write line~4 as
\begin{lstlisting}
…
final var messageProvider = getMessageProvider();
…
\end{lstlisting}
making it less visible that the class name is used for the name of the local variable.

\keeplisting{11}
This variant is less recommended; in fact, it is discouraged:
\begin{lstlisting}
// AVOID!!!! Don't use "my" or "the" prefix!!!
public final String retrieveMessage( final String string,  final String... strings )
{
    final var theMessageProvider = getMessageProvider();
    final var myString = theMessageProvider.getMessage( string );
    final var retValue = String.format( myString, strings );
    
    //---* Done *----------------------------------------------------
    return retValue;
}   //  retrieveMessage()
\end{lstlisting}

Sometimes it is also a good idea to use the type name as a suffix or prefix for the name of the local variable, especially if the current block declares more than one variable of the respective type. In such a case, the rest of the name could be used to indicate how variables belong together or what they distinguishes them from each other.
\keeplisting{8}
\begin{lstlisting}
public final ResultData loadData( Connection connection, … )
{
    final Statement customerStatement = …
    final Statement orderStatement = …

    final ResultSet customerResultSet = customerStatement.execute();
    final ResultSet orderResultSet = orderStatement.execute();
    …
}   //  loadData()
\end{lstlisting}

\keeplisting{7}
In case the first part of the variable name has to be an acronym of some kind, it will be written with all lower case – even when the acronym is usually written in all uppercase letters:
\begin{lstlisting}
// OK
final String htmlHeader;
final String xmlElement;
final String jsonObject;
final String svgNumber;
\end{lstlisting}
\keeplisting{6}
instead of
\begin{lstlisting}
// AVOID!
final String hTMLHeader;
final String xMLElement;
final String jSONObject;
final String sVGNumber;
\end{lstlisting}

Single-letter variable names should be avoided except for temporary \bdq{throwaway} variables. Some of these are widely used and have already a fixed meaning; so is \lstinline|i| very common for the run value of a classical \lstinline|for|\index{for} loop.

\keeplisting{2}
\lstinline|i| can be an \lstinline|int|:
\begin{lstlisting}
for( var i = 0; i < max; ++i ) { … }
\end{lstlisting}
\keeplisting{7}
or it can be an \lstinline|Iterator|  \autocite{ORACLE_DOC_ITERABLE_INTERFACE,ORACLE_DOC_ITERATOR_INTERFACE}:
\index{java.lang!Iterable}\index{java.lang!Iterable!iterator()}\index{java.lang!Iterator}\index{java.lang!Iterator!hasNext()}\index{java.lang!Iterator!next()}
\begin{lstlisting}
final Iterable<?> iterable = …
for( final var i = iterable.iterator(); i.hasNext(); ) 
{
    final var current = i.next(); 
    … 
}
\end{lstlisting}
\keeplisting{10}
\lstinline|e| is the common name for the exception\index{exception} in a \lstinline|catch|\index{try!catch} block:
\index{java.io!IOException}
\begin{lstlisting}
try
{
    …
}
catch( final IOException e )
{
    //---* Handle the exception *------------------------------------
    e.printStackTrace();
}    
\end{lstlisting}

\keeplisting{13}
If the caught exception\index{exception} is not referenced in the \lstinline|catch|\index{try!catch} block, use the underscore (\bdq{\lstinline|_|}) instead of a local variable; that is the \textit{unnamed exception}\index{exception!unnamed exception}:
\index{java.io!IOException}
\begin{lstlisting}
var result = null;
try
{
    result = …
    …
}
catch( final IOException _ )
{
    //---* Use default value instead *-------------------------------
    result = DEFAULT_VALUE;
}    
\end{lstlisting}

For temporary strings, \lstinline|s| is well established, as \lstinline|o| is for (temporary) objects of an unspecified type, and \lstinline|n| for a number.

\subsection{Reserved Names}
Some names for local variables are reserved or otherwise fixed – at least you should avoid to use them in another way than described here.

\paragraph{\lstinline|e|}\label{lbl:e}– I already mentioned the single-letter variable name \lstinline|e| that is used for the caught exception in a catch block.
\index{java.io!IOException}
\begin{lstlisting}
try
{
    …
}
catch( final IOException e )
{
    //---* Handle the exception *------------------------------------
    e.printStackTrace();
}    
\end{lstlisting}

\keeplisting{18}
\paragraph{\lstinline|retValue|}\label{lbl:RetValue}– The variable name \lstinline|retValue| is reserved for the return value of a method\index{method}; basically a method\index{method} that does not have \lstinline|void| as the return value will return always \lstinline|retValue|, \lstinline|this| or an attribute:
\begin{lstlisting}
public final int signum( double d )
{
    final var retValue = (d < 0.0) ? -1 : ((d > 0.0) ? 1 : 0);

    //---* Done *----------------------------------------------------
    return retValue;
}   //  signum()

public final Builder<T> setFlag( final Flag flag )
{
    if( nonNull( flag ) ) m_Flags.add( flag );
    
    //---* Done *----------------------------------------------------
    return this;
}   //  addFlag()

public final int getValue() { return m_Value; }
\end{lstlisting}

\paragraph{\lstinline|result|}\label{lbl:Result}– Similarly, the local variable name \lstinline|result| is reserved for the return values of lambdas\index{lambda} (see chapter \tqfullvref{sec:LambdaResults}) and for the results of \lstinline|case|\index{switch!expression}\index{switch!case} blocks (see chapter \tqfullvref{sec:CaseResults}). Avoid to use the name \lstinline|result| for a local variable in any other context. But usually, you should not need a local variable for the return values of lambdas\index{lambda} or \lstinline|case|\index{switch!expression}\index{switch!case} blocks.

\keeplisting{2}
We can write the \lstinline|signum()| method\index{method} as a lambda\index{lambda} like this:
\index{java.util.function!Function}
\begin{lstlisting}
public final Function<Double,Integer> signum = d -> (d < 0.0) ? -1 : ((d > 0.0) ? 1 : 0);
\end{lstlisting}

\keeplisting{19}
or with a \lstinline|switch| expression\index{switch!expression}\footnote{The code works, but it does not make much sense to implement \lstinline|signum()| like this.}:
\begin{lstlisting}
final var signum = switch( v )
{
    case null -> throw new NullArgumentException( "v" );
    case Byte byteValue -> (byteValue < 0) ? -1 : ((byteValue > 0) ? 1 : 0);
    case Double doubleValue -> (doubleValue < 0.0d) ? -1 : ((doubleValue > 0.0d) ? 1 : 0);
    case Float floatValue -> (floatValue < 0.0f) ? -1 : ((floatValue > 0.0f) ? 1 : 0);
    case Integer intValue -> (intValue < 0) ? -1 : ((intValue > 0) ? 1 : 0);
    case Long longValue -> (longValue < 0l) ? -1 : ((longValue > 0l) ? 1 : 0);
    case Short shortValue -> (shortValue < 0) ? -1 : ((shortValue > 0) ? 1 : 0);
    default -> throw new IllegalArgumentException( v.getClass().getName() + " not supported" );
}
\end{lstlisting}

\paragraph{\lstinline|buffer|}– A temporary buffer is named \lstinline|buffer|, and it does not matter if it is a \lstinline|java.lang.StringBuilder| or \lstinline|java.lang.StringBuffer|, an implementation of \lstinline|java.util.List|, another collection type, or any other type that can be used as a buffer.

\paragraph{\lstinline|in|, \lstinline|out|, and \lstinline|err|}– Do not use the names \lstinline|in|\index{java.lang!System!in}, \lstinline|out|\index{java.lang!System!out}, and \lstinline|err|\index{java.lang!System!err} as names for local variables. Although these names are not reserved words, they should be treated as such. They are the names for the variables from the class \lstinline|java.lang.System|\index{java.lang!System} \autocite{ORACLE_DOC_SYSTEM_CLASS}, representing the system streams \bsq{standard in} (\verb#stdin#), \bsq{standard out} (\verb#stdout#) and \bsq{standard error} (\verb#stderr#). They can be accessed qualified by the class name (as \lstinline|System.out|, but quite often, they are statically imported. A local variable with the same name would cause a name clash, or at least it could cause some confusion.

\paragraph{\lstinline|_| (The underscore)}– is a keyword \autocite{ORACLE_DOC_LANGUAGE_SPECIFICATION:Keywords} with a special meaning \autocite{ORACLE_DOC_LANGUAGE_SPECIFICATION:Declarations}. It can be used instead of a local variable where such a variable is syntactically required, but semantically obsolete.

We have seen it already as the unnamed exception in a \lstinline|catch|\index{try!catch} block, but it can be used also with a \verb#try-with-resources#\index{try-with-resources} where a reference to the resource is not used:
\begin{lstlisting}
…
AutoLock m_AutoLock = AutoLock.of( new ReentrantLock() );
…
try( final var _ = m_AutoLock.lock() )
{
    // Do something
    …
}
\end{lstlisting}
This example is explained in detail in chapter \tqfullvref{sec:TryWithResources}.

\subsection{Local Variables in Lambdas}
Local variables inside lambdas\index{lambda} are just like any other local variable and their naming follows the same rules. The only exception is that a lambda\index{lambda} does not use \lstinline|retValue| for a return value, but \lstinline|result| – refer to chapter \tqfullvref{sec:LambdaResults} for the details.

\subsection{Summary}

\subsubsection{Principles}
\begin{enumerate}[label=P\arabic*.]
	\item{Use \textit{camelCase} for the names of local variables, with a lowercase first letter.}

	\item{The names of local variables should be short yet meaningful.}
	
	\item{Don't use \bsq{Hungarian Notation}\index{Hungarian Notation} or another kind of prefix!}
	
	\item{Usually use the singular, but for collections and arrays, use the plural form.}
	
	\item{Naming a local variable after its type is always an option.
	
	Also using the type as a suffix or prefix.}
	
	\item{If the name starts with an acronym, write that all lowercase.}
	
	\item{Usually don't use single-letter names.
	
	But for some well established use cases, single-letter names are ok.}
	
	\item{Some names are reserved:
	\begin{itemize}[nosep]
		\item{\lstinline|buffer|}
		\item{\lstinline|e|}
		\item{\lstinline|err|}
		\item{\lstinline|in|}
		\item{\lstinline|out|}
		\item{\lstinline|result|}
		\item{\lstinline|retValue|}
	\end{itemize}}
	
	\item{All this is also valid for local variables in lambdas\index{lambda}.}
\end{enumerate}
