\chapter{Maintenance Comments}\label{sec:MaintenanceComments}
Even after first released, it is very likely that source code is modified more than once during its lifetime: bugs are fixed, functionality is added or removed, refactorings are applied, or the code is migrated to other platforms or newer versions of the programming language, of the underlying libraries, of the connected systems and/or of the operating system.

Often those changes got commented in the source; these comments are  are usually referred to as \bdq{Maintenance Comments}.

Some organisations even defined rules on how these maintenance comments have to look like, as in the sample below:
\keeplisting{20}
\begin{lstlisting}
…
//<<BEGIN FSP-0815 – applied by Mirabel Madrigal
<Additional Code>
…
//>>END FSP-0815
…
//<<BEGIN FSP-4711 – applied by Richard Rawlings
//<Old Code>
//…
//>><<
<New Code>
…
//>>END FSP-4711
…
//<<BEGIN FSP-4917 – applied by Donald Duffy
//<Old Code>
//…
//>>
<Unmodified Code>
…
//<<
<New Code>
…
//>>END FSP-4917
…
\end{lstlisting}

The abbreviation \bsq{\texttt{FSP}}\index{FSP|see {Field Service Patch}} stands for \bdq{Field Service Patch}\index{Field Service Patch}.

Although it looks good at a first glance, it has proved that this kind commenting maintenance changes is not a good practice at all, and a really bad practice if dealing with code that is managed by an SCCS\index{SCCS} like Git\index{Git} \autocite{Git} or Subversion\index{Apache Subversion} \autocite{APACHE_SUBVERSION}.

\begin{itemize}
	\item{First, this practice causes problems for the compare tools coming with the SCCS\index{SCCS} – at least it will make it more difficult to read the comparison results from those tools.That's because most comparison tools will recognise the out-commenting of the old code as a change and the new code as additional code instead of the replacement for the old code. This is at least confusing when code revisions are made on the fix. And the main function of those comments – documenting the changes – is much better served by the SCCS\index{SCCS} tools themselves.}
	
	\item{Second, this gets even worse when the fix needs a fix. Just think about overlapping changes, like \texttt{FSP-4712} changes lines from the new code of \texttt{FSP-4711}, together with lines directly below, or changes that has to be partially reverted, and so on.}
	
	\item{And finally, the comments does not help to identify if you are currently running the patched code, or the old one. I will discuss this in more detail \hyperref[loc:CommentVsAnnotations]{below}.}
\end{itemize}

Nowadays, change requests of all kinds are tracked within ticket systems like Jira\index{Jira|see {Atlassian Jira}}\index{Atlassian Jira}\footnote{Of course, Jira is more than just a \textit{ticket system}, but it serves quite well as one.} \autocite{AtlassianJira}, where each ticket (= change request) gets an id (like those \texttt{FSP}\index{Field Service Patch} number above), and this id is also used when the code related to the change request is committed to the SCCS\index{SCCS}, as part of the commit label.

All SCCS\index{SCCS} provides a feature to search for the contents of commit labels, and that allows you to identify the changes made for a given change request, much better as any comment could do.

On the other hand, nothing can be said against adding a comment to code that refers to the change request by its ticket id. So when you added a method or field, you can use the Javadoc\index{javadoc} tag \bdq{\nameref{sec:TagSince}}\index{since@"@since} with the ticket id instead or in addition of the version number. It can be even used when the method was only modified, as shown on page \pageref{sec:TagSince}.

Usually, functionality will not be removed immediately, especially not when exposed through the API. Before that, it is marked as \bdq{deprecated} for several consecutive versions. This is done using both the \bdq{\nameref{sec:TagDeprecated}}\index{deprecated@"@deprecated} Javadoc\index{javadoc} tag and the \lstinline|@Deprecated| annotation\index{annotation!deprecated@"@deprecated}.

In both cases, the maintenance comments for the change are also documentation comments that are externalised. This may be wanted or not, although for API changes, it is mandatory.

Alternatively, you just add the ticket id as a real comment to the location(s) for the changes. This clearly indicates that changes have taken place; for the details, one can then consult the SCCS. 
 
Above I said that it is a drawback of maintenance comments that they do not allow to identify whether the running code does contain a specific change\pslabel{loc:CommentVsAnnotations}. This is primarily of interest for long-running programs, such as various types of servers\index{server}, as well as for server-based applications\index{product type!server-based application} (refer to \tqref{sec:ServerbasedApplication}).

If this is a requirement for your product, you should consider to use dedicated annotations\index{annotation} instead of maintenance comments.\footnote{This is discussed more generally in \tqfullvref{sec:CommentVsAnnotations}.} I provide an example of such an annotation\index{annotation} in chapter \tqfullvref{sec:PatchIdentification}; it can be used to mark program elements that were affected by a change request of some kind.

Such an annotation\index{annotation} can provide the the ticket id of the change request, together with a description of the issue that was addressed. This annotation\index{annotation} replaces a comment about the applied patches, with the advantage that it can easily be retrieved from the code, even at runtime.

The relevant details about the fix/change/enhancement can now be found in the SCCS\index{SCCS} and/or in your ticket system, referenced through the id provided with the annotation\index{annotation}.

When annotations\index{annotation} are used to track and document changes to the source code, the actual maintenance \textit{comments} are reduced to simple references to the ticket IDs cited within those annotations – as shown in lines~50 and 55 in the example above.
